# Проверка Rust-порта перед мержем — 2026-11-02

Проверена ветка `codex/rust-server-parity`. База этой проверки — `f43a4aa`;
исправления и артефакты ниже входят в коммит с этим отчётом. Протокол и клиентские
проекты не менялись. Исторические результаты Node/Rust на VPS остаются в
[отдельном отчёте](benchmarks/vps-rust-20261102.md); приведённые здесь цифры —
локальное сравнение Rust **до и после ревью**, а не новый замер VPS.

## Найдено и исправлено

| Проблема | Изменение и проверка |
| --- | --- |
| Учёт попыток подключения вставлял новый IP до проверки размера таблицы. Поток отвергнутых адресов мог увеличивать её сверх лимита до истечения TTL. При заполнении также отклонялись уже известные IP. | Проверка до вставки; модуль `admission` и RAII-разрешение активного подключения. Тест отвергает 996 новых адресов без роста таблицы, проверяет известный адрес, освобождение разрешения и TTL. |
| Состояние обрабатывалось рабочим потоком, но health/push/telemetry могли ждать его mutex прямо на сетевом executor. | Единственный владелец `Server` в `state.rs`, ограниченная очередь команд и асинхронные ответы. Тест с одним async-потоком подтверждает, что ожидание состояния не мешает другой async-задаче освободить заблокированную работу. |
| Обычный JSON разбирался дважды; исходящее сообщение сериализовалось для проверки размера и повторно для отправки. | Немедленная обработка использует уже проверенный JSON; рассылка разделяет один сериализованный кадр. Отложенные сообщения сохраняют только ограниченные по размеру wire bytes. |
| Удаление комнаты из упорядоченной таблицы сдвигало остальные комнаты при каждом JSON-сообщении. | `swap_remove` на этом пути. Список комнат явно сортируется по ID; порядок участников, определяющий смену владельца, сохранён. |
| Сброс логов мог зависнуть на заполненной очереди ещё до начала таймаута. Ответ Close тоже не имел ограничения ожидания записи. | Общий дедлайн постановки/сброса логов, тест заполненной очереди; ограниченное ожидание Close с отменой при остановке. |
| Немедленная отмена push-задачи при штатной остановке могла оборвать сохранение результата доставки. Это проявилось в тесте повторной доставки после рестарта во время рефакторинга. | Push/telemetry получают ограниченное время на завершение, затем отменяются. Тесты уведомлений, дедупликации и рестарта проходят. Аварийная остановка по-прежнему не даёт гарантии exactly-once у внешнего провайдера. |

## Память и освобождение ресурсов

Native-тест с отслеживаемым владельцем `Bytes` проверяет освобождение одного и того
же буфера из отложенной очереди и очереди сокета: после disconnect очередь задержки
пуста, после удаления получателя уничтожен последний владелец. Другой тест
проверяет завершение потока состояния и освобождение его данных после удаления
последнего отправителя. Циклов владения `Arc`, `mem::forget`, `Box::leak` и
собственного `unsafe` при просмотре кода не обнаружено.

Локальный сценарий на итоговом release-бинарнике: 64 клиента, 16 комнат по четыре
игрока, в каждой 128 KiB сохранённого состояния и незавершённая загрузка 256 KiB.
Чередуются `leaveRoom` и внезапный обрыв всех сокетов. TTL аккаунта — 300 мс,
интервал обслуживания — 50 мс. После каждого цикла `accounts`, `online`, `rooms`
и `pendingConnections` должны стать нулевыми. Дисковая квота тестовых состояний —
8 MiB; файлы сохранений могут оставаться на диске по правилам persistence.

Основной прогон: **30 циклов, 1920 подключений**. После очистки:

- RSS: **8,75–9,38 MiB**; максимум RSS под нагрузкой — **17,70 MiB**.
- Private committed bytes: **2,36–4,72 MiB**; медиана первых/последних десяти
  циклов — **3,16 / 3,16 MiB**.
- Дескрипторы: **119** после каждого цикла.
- Все четыре счётчика состояния возвращались к нулю.

Дополнительный прогон с `SEND_DELAY_MS=100`: **12 циклов, 768 подключений**.
После очистки RSS — **8,56–9,37 MiB**, private memory — **2,22–4,36 MiB**,
дескрипторов неизменно **119**; все четыре счётчика каждый раз обнулялись.
Всего проверено **2688 подключений**. Исходные данные:
[основной прогон](benchmarks/premerge-20261102/memory-direct.json),
[отложенные сообщения](benchmarks/premerge-20261102/memory-delayed.json).

В проверенном сценарии накопление живых ресурсов не выявлено. Это не доказательство
отсутствия любых утечек: тест длится минуты, а не дни; ASan/Miri/Valgrind не
запускались. RSS включает страницы, оставленные аллокатором для повторного
использования, поэтому отдельно измеряется private memory и проверяются владельцы.

## Производительность после правок

Windows x64, Ryzen 7 9800X3D, Node 26.4.0 как генератор нагрузки. На каждый вариант
три повторения, 16 комнат / 32 клиента, секунда прогрева и три секунды измерения.
Порядок вариантов чередуется. Один RTT — два прохода через relay. Нет TLS, дисковых
сохранений, push и telemetry. Сборка и другие нагрузочные тесты во время замеров
не запускались. JSON-размер — приблизительный размер входного сообщения;
бинарный размер точный. Ниже медианы трёх повторений, RSS под нагрузкой.

| Сообщение | RTT/с до → после | Изменение | CPU мс / 1000 RTT до → после | RSS MiB до → после |
| --- | ---: | ---: | ---: | ---: |
| JSON ~512 B | 24 356 → 26 005 | +6,8% | 53,76 → 49,15 | 12,61 → 9,11 |
| JSON ~32 000 B | 7 262 → 7 812 | +7,6% | 197,19 → 158,57 | 13,86 → 11,56 |
| Binary 512 B | 25 241 → 27 341 | +8,3% | 44,18 → 41,05 | 12,50 → 9,04 |
| Binary 32 000 B | 6 915 → 7 084 | +2,4% | 89,40 → 81,34 | 13,80 → 11,45 |

Для большого бинарного кадра разброс между повторениями существенный; +2,4% нельзя
считать убедительным доказательством ускорения. JSON потребляет на 8,6–19,6% меньше
CPU на операцию в этом сценарии. Результаты нельзя переносить напрямую на WAN,
максимальное число игроков или VPS с одним vCPU. Генератор и сервер делят одну
машину; это проверка регрессии и направления эффекта, не оценка предельной ёмкости.

- После: `8344bdf3f676d50b24302057e9f67fb10c87e22f1679bda331e7a6b0d5707148`.

- `npm run check`: 128 успешных тестов, 4 пропуска; TypeScript и ESLint проходят.
- `npm run check:rust`: 13 native-тестов; адаптированный набор — 129 успешных,
  3 пропуска на Windows; rustfmt и Clippy с запретом предупреждений проходят.
- Общий JS-набор содержит также reference-only тесты; его число не является
  количеством отдельных Rust-тестов. Два теста с monkeypatch Node `ws` заменены
  native-проверками лимитов; SIGTERM проверяется только на POSIX.
- Реальный General-recovery: три браузерных клиента, три хода, потеря хоста и
  повторный вход. Канонические миры совпали на всех контрольных точках, ошибок — 0.
  [Синтетические контрольные точки](benchmarks/premerge-20261102/general-client.json).
- `npm audit`: 0 известных уязвимостей. Точные версии 202 registry-пакетов из
  `Cargo.lock` проверены через OSV QueryBatch: совпадений с advisories нет.
  Это проверка базы на дату ревью, не аудит исходников всех зависимостей.
- CI на Windows и Ubuntu теперь дополнительно выполняет три цикла очистки с
  16 клиентами и состоянием 64 KiB на комнату. Он проверяет освобождение состояния,
  а не нестабильный между машинами порог RSS. Статус каждого коммита доступен в
  [GitHub Actions для ветки](https://github.com/apxapob/no_logic_game_server/actions?query=branch%3Acodex%2Frust-server-parity).

## Оценка архитектуры и оставшиеся ограничения

Для relay без игровой логики разделение на transport, последовательный владелец
состояния, protocol, store, push и telemetry разумно. Сетевые операции не удерживают
состояние через `await`; порядок переходов и совместимость проще проверить.
Выходные очереди ограничены байтами, очередь команд — количеством элементов.
Структуры комнат и игроков имеют явный жизненный цикл. Извлечён общий сборщик
ресурсов процесса для benchmark и теста очистки. Две реализации, Node и Rust,
пока намеренно остаются эталоном и вариантом отката; удалять Node перед завершением
миграции не стоит.

Ограничения, которые следует учитывать перед ростом нагрузки:

1. **Нет общего бюджета RAM для состояний комнат и загрузок.** При стандартных
   `MAX_ROOMS=128` и `MAX_SESSION_BYTES=16 MiB` только сохранённые состояния могут
   занять 2 GiB; незавершённые загрузки добавляют до такого же объёма. Это оценка
   допустимых лимитов, не измеренный расход. `SESSION_MAX_BYTES` относится к диску
   и не предотвращает исчерпание RAM. Поведение унаследовано от Node.
2. **Очереди persistent-уведомлений требуют политики backlog.** При долгой
   недоступности доставки новые immediate jobs могут накапливаться без общего
   лимита. Это удержание нужных для повторной доставки данных, но ресурсный риск;
   автоматическое удаление или отказ в новых заданиях изменит текущие гарантии.
3. **Переходы состояния и дисковые операции последовательны.** Один медленный
   диск задержит команды всех комнат. Если профиль нагрузки покажет этот предел,
   следующий шаг — отдельная очередь persistence и/или разделение комнат между
   владельцами, с сохранением порядка операций и атомарности сохранений.
4. `server.rs` остаётся крупным; конфигурация и DTO частично представлены
   `serde_json::Value`. Типизированная конфигурация и выделение session-команд
   улучшат сопровождение, но такой рефакторинг требует отдельной проверки паритета.
5. Реальные Unity Editor/device-сценарии двух Unity-клиентов и доставка через живой
   FCM здесь не проверялись; есть wire-контракты и локальный mock-провайдер.

Исправления этого ревью не активировались на VPS. Мерж и смена production-релиза
не являются частью проверки.
