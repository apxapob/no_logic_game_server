# Rust на apxapob.com: повтор нагрузочного теста

Дата: 2 ноября 2026 года, Москва. Машинные отметки времени — UTC, 1 ноября.
Рабочий сервер переведён на Rust, ревизия `17cf3e1260f9b00d720e6c15599f33296b80186d`,
ветка `codex/rust-server-parity`. Клиенты и их адреса не менялись.

## Что получилось

В подтверждающем тесте на 2048 соединениях с сообщением раз в 5 секунд обе версии
доставили 100% сообщений без разрывов за 180 секунд. У Rust CPU самого backend
снизился с 53.84% до 25.39%
(−52.8%), занятость всего VPS —
с 82.25% до 48.33%. Пиковая анонимная память —
110.1 → 98.9 МиБ. Это измерение заданной
нагрузки, а не доказательство удвоения максимального числа игроков.

Выбран входной буфер **16 КиБ**: он оказался быстрее 128 КиБ на небольших кадрах,
а на максимальном проверенном кадре 64 КиБ медианная скорость практически
совпала при меньшем расходе CPU. 300+ МиБ RAM сами по себе не были проблемой
на VPS с примерно 2,6 ГиБ RAM. Размер выбирался по скорости, а не ради экономии
памяти любой ценой. Автовыбор по игре не добавлялся.

## Откуда взят прежний тест

Найден чат «Проверь второй сервер в pass» от 28 октября,
`01a18283-bca5-7d81-8ea0-e18e391eadf6`. Прежняя папка с артефактами отсутствовала;
из истории изменений восстановлены отчёт и финальный генератор нагрузки.
[Исторический отчёт](vps-node-20261028.md) сохранён отдельно. Старые сырые замеры
не восстановлены: числа за 28 октября — из того отчёта, не новые измерения.

Использован тот же генератор: заменены только пути `require` библиотеки `ws`.
SHA-256 исходного и адаптированного генераторов записаны в
[manifest.json](vps-20261102/manifest.json). Сценарий остался прежним:
JSON `shareGameState` от владельца трём участникам, JSON `sendTo` от участников
владельцу, комнаты по четыре игрока. Сжатый бинарный трафик не подменяет старую нагрузку.

| Профиль | Частота / клиент | Состояние / команда | Измерение |
|---|---:|---:|---:|
| Частый обмен, подробные логи | 20/с | 1024 / 128 байт | 45 с на ступень; 96 игроков — 180 с |
| Частый обмен, без подробных логов | 20/с | 1024 / 128 байт | 128 и 256 игроков по 60 с |
| Редкие команды, подробные логи | 0,2/с | 8192 / 256 байт | 2048 игроков — 180 с |

Сохранены прогрев, плавное подключение, heartbeat и пороги остановки: доставка
менее 99,9%, заданная частота менее 95%, p95 выше 5 секунд либо разрыв/ошибка.
Для получения запоздавших сообщений оставалось до 5 секунд после измерения.
Ступени после нарушения порога не запускались. На финальном Rust повторена
лестница частого обмена с 16 игроков, оба прогона без логов, подтверждение
96 игроков и подтверждение 2048 игроков. Лестница редких команд 256–2048
выполнялась на первой Rust-сборке с буфером 128 КиБ; эти числа выделены отдельно.

## Стенд и смысл метрик

Тот же VPS: **1 vCPU**, около 2,6 ГиБ RAM, Caddy/TLS. Внешний генератор — Windows,
Node 26.4.0, ws 8.22.0. Свежий Node baseline — действовавший перед переключением
релиз `20261031-persistent-dc09ddf`, Node 24.22.1; файлы `src` совпали с эталоном
`6e7d10c8bebb3bbcf5c156ed71589dcc1f93b139`. Это более новая версия, чем релиз
`c6ff3e3` из теста 28 октября, поэтому ниже есть и историческое, и свежее сравнение.

Нагрузка шла на временный экземпляр через отдельный путь того же WSS-домена.
Рабочий Rust продолжал работать отдельным процессом. Запуски были последовательными,
без параллельной компиляции. У обоих временных backend — лимит cgroup 768 МиБ,
у Node heap 512 МиБ; одинаковые квоты подключения и сообщений. Сохранение сессий,
push и телеметрия на нагрузочном экземпляре отключены, как в старом тесте.
Рабочая конфигурация, включая подробные логи и телеметрию, сохранена.

CPU backend — учёт отдельной cgroup; 100% означает одно полностью занятое ядро.
CPU VPS включает Caddy, системную работу и, по формуле старого анализатора,
**steal time гипервизора**. Отдельный `hostStealMean` сохранён; он менялся между
прогонами, поэтому небольшие различия не следует считать точным выигрышем языка.
Память в таблицах — **пик анонимной памяти cgroup**, не сумма с файловым кэшем
логов. Значение cgroup около 768 МиБ включало этот кэш и не означало такой RSS
процесса. Задержка — от внешнего отправителя до внешнего получателя, включая
оба сетевых участка и TLS.

## Буферы: отдельный эксперимент

В Tungstenite 0.28 исходный `read_buffer_size` равен 128 КиБ на соединение.
При тысячах соединений это заметная стартовая аллокация. Этот параметр также
ограничивает порцию одного чтения. После разбора заголовка библиотека резервирует
память под весь кадр; порция 16 КиБ **не ограничивает сообщение 16 КиБ** и
не требует ждать заполнения буфера. Лимит сообщения остался прежним — 65536 байт
по умолчанию. Отправка выполняется сразу (`write_buffer_size=0`, `send` с flush).
Лимит очереди исходящих сообщений и поведение при медленном получателе не менялись.
В этой версии библиотеки `FrameCodec::read_in` перед чтением расширяет буфер
нулями до размера доступной порции. Поэтому большой буфер может добавлять работу
с памятью на мелких сообщениях. Вклад обнуления отдельно профилировщиком
не измерялся.

На том же VPS последовательно проверены два неизменяемых бинарника: `3341fea`
(128 КиБ) и `17cf3e1` (16 КиБ). По три повтора с чередованием порядка, 32 клиента,
16 двухместных комнат, 1 с прогрева + 5 с измерения, без TLS и подробных логов.
Генератор и сервер — разные процессы **на одном vCPU**. Это микротест, не оценка
внешней пропускной способности VPS. Одна RTT включает две пересылки relay.
Медианы:

| Кадр | RTT/с, 128 КБ | RTT/с, 16 КБ | Изменение скорости | CPU мс / 1000 RTT, 128 → 16 КБ | Изменение CPU |
|---|---:|---:|---:|---:|---:|
| 512 байт | 4068 | 5221 | +28.3% | 120.1 → 78.9 | -34.3% |
| 32000 байт | 1264 | 1625 | +28.6% | 251.5 → 201.4 | -19.9% |
| 65536 байт | 750 | 756 | +0.8% | 429.7 → 341.3 | -20.6% |

Для 64-КиБ кадров результаты отдельных повторов заметно колебались; +0,8%
означает сопоставимую скорость в пределах разброса. CPU на операцию у 16-КиБ
варианта ниже во всех трёх размерах. При редком обмене 2048 соединений потребляли
313,2 МиБ с 128-КиБ буфером (60 с) и 98,9 МиБ с 16-КиБ (180 с); продолжительность
этих двух внешних прогонов различалась. Сырая серия и параметры —
[buffer-comparison.json](vps-20261102/buffer-comparison.json).

Динамическое переключение по названию игры не требуется по этим данным.

кадров и скорость чтения конкретного соединения. Это не должно добавлять игровую
логику в relay или требовать изменений клиентов.

## Развёртывание и проверки

Рабочий бинарник собран на Linux в release-режиме, rustc 1.99.1:
SHA-256 `605f9f227632db28eb69cedfa910b2a8e26da9d50e8797c8f94317c43a84c779`.
Локальная проверка форматирования/Clippy использует Rust 1.96.0; CI закреплён
на этой проверенной версии, чтобы новый deprecation-warning более свежего
компилятора не ломал проверку с запретом предупреждений.

- 8 native Rust tests; адаптированный набор: Linux 130 passed / 2 skipped,
  Windows 129 passed / 3 skipped. Часть общего набора — JS-only тесты эталона,
  поэтому это не число независимых Rust-тестов.
- Публичные WSS-проверки корня и `/general/`: JSON, адресный и широковещательный
  binary v1 с 32-КБ данными, legacy `0xF8`, смена владельца и повторный вход.
- Ранее на этой ветке неизменённые браузерные клиенты General-recovery прошли
  три хода, смену владельца и восстановление с одинаковым состоянием мира.
  Для Unity-клиентов проверен wire-протокол; прогон на устройствах не выполнялся.

Переключение выполнялось при нуле активных игроков, с копией сессий и сохранением
исходного Node-релиза для отката. Одна промежуточная попытка запуска столкнулась
с правами нового каталога (umask 077); автоматически восстановлена предыдущая
Rust-сборка, права исправлены, повторное переключение прошло. После успешного
развёртывания счётчик перезапусков — 0.

Для отката нужно остановить сервис штатно, вернуть `current` на сохранённый
Node-релиз, удалить добавленный `99-rust.conf` с переопределением ExecStart,
выполнить daemon-reload и запустить сервис. Формат сессий совместим в обе стороны;
старый и новый процессы нельзя одновременно запускать на одном каталоге сессий.
Закрытый резервный каталог на VPS содержит исходный unit/env и снимки сессий;
секреты и содержимое сессий в репозиторий не включены.

После тестов временные backend, монитор и таймер остановлены, порт 8082 закрыт,
маршрут нагрузки удалён, освобождён примерно 1 ГБ временных логов.
Caddyfile восстановлен побайтно, production env не менялся.
Итоговая проверка сохранена в [final-verification.json](vps-20261102/final-verification.json).

## Ограничения и воспроизведение

Это короткие синтетические тесты. Они не проверяют 5000 игроков, суточную работу,
массовое одновременное переподключение, диск под реальной нагрузкой или live FCM.
На одном vCPU невозможно подтвердить масштабирование по ядрам: у Rust отдельные
потоки сети и состояния, но переходы состояния комнат пока сериализованы.
При частом обмене значительную часть CPU занимает Caddy/TLS; ускорение backend
не переносится автоматически в такое же увеличение вместимости всего VPS.

Рабочие квоты сохранены: 5000 соединений глобально и 256 на IP. За текущим
локальным reverse proxy адрес подключения общий, поэтому лимит на IP может
ограничить фактический доступ раньше глобального. Временный стенд использовал
8192 на IP; его результат не означает автоматического изменения рабочих квот.

Исходные события, все измеренные ступени, параметры и метрики:
[runs.jsonl](vps-20261102/runs.jsonl), [summary.json](vps-20261102/summary.json),
[profiles.json](vps-20261102/profiles.json),
[metrics.jsonl.gz](vps-20261102/metrics.jsonl.gz),
[manifest.json](vps-20261102/manifest.json). Архив содержит метрики ресурсов,
а не env, ключи, сессии или полезные данные игроков.

Для повторения подготовить отдельный экземпляр и WSS-путь на разрешённом сервере
с параметрами manifest; заменить `url` и `output` выбранного профиля и выполнить
`node scripts/vps-loadtest.cjs profile.json`. На VPS собирать метрики командой
`python3 scripts/vps-monitor.py /private/path/metrics.jsonl --seconds 3600`.
Затем поместить метрики в `RUN/results/metrics.jsonl`, события в
`RUN/results/run.jsonl` и выполнить
`python scripts/vps-analyze.py RUN results/run.jsonl`.
Не запускать генератор одновременно со сборкой или вторым тестом на этом VPS.
После прогона убрать временные сервис и маршрут.
